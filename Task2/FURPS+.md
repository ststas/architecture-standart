# Task2. FURPS+ таблица

В таблице отмечены архитектурно-значимые требования.  
Обозначение `ASR` - требование влияет на архитектурное решение.

| Код      | Категория      | Требование                                                                                                                   | ASR | Комментарий                                                                                                                |
| -------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------- | --- | -------------------------------------------------------------------------------------------------------------------------- |
| F-01     | Functionality  | На сайте клиент должен видеть список доступных депозитов с актуальными ставками.                                             | Да  | Требуется источник актуальных ставок вместо текущих XLS-файлов.                                                            |
| F-02     | Functionality  | На сайте новый клиент должен иметь возможность подать заявку на депозит, указав номер телефона и Ф. И. О.                    | Да  | Передаются персональные данные, нужен защищённый канал и передача заявки в дальнейший процесс обработки.                   |
| F-03     | Functionality  | Заявка с сайта должна попадать в систему, доступную менеджеру кол-центра.                                                    | Да  | Влияет на интеграцию сайта, системы кол-центра и/или промежуточного сервиса заявок.                                        |
| F-04     | Functionality  | Менеджер кол-центра должен видеть заявку и иметь возможность предложить клиенту особые условия.                              | Да  | Требует поддержки процесса спецусловий и доступа к данным заявки.                                                          |
| F-05     | Functionality  | Новый клиент после заявки на сайте должен пройти идентификацию в отделении.                                                  | Да  | Бизнес-ограничение MVP: открытие депозита для нового клиента не завершается полностью онлайн.                              |
| F-06     | Functionality  | В интернет-банке клиент должен видеть список доступных депозитов с актуальными ставками.                                     | Да  | Интернет-банк должен получать ставки из целевого источника, а не из XLS вручную.                                           |
| F-07     | Functionality  | В интернет-банке клиент должен видеть персонализированные ставки, рассчитанные для него.                                     | Да  | Требует интеграции с механизмом расчёта/согласования персональной ставки и клиентскими данными.                            |
| F-08     | Functionality  | Клиент интернет-банка должен подать заявку на открытие депозита, указав счёт списания и сумму депозита.                      | Да  | Влияет на фронт интернет-банка, процесс заявок и связь с АБС.                                                              |
| F-09     | Functionality  | Операция открытия депозита в интернет-банке должна подтверждаться СМС-кодом.                                                 | Да  | Используется существующий SMS-функционал ядра; важно не закладывать обязательную доработку подрядчиком.                    |
| F-10     | Functionality  | На этапе MVP заявку на открытие депозита обрабатывает менеджер бэк-офиса.                                                    | Да  | Процесс не должен проектироваться как полностью автоматический end-to-end.                                                 |
| F-11     | Functionality  | Менеджер бэк-офиса должен подтверждать условия депозита в АБС.                                                               | Да  | АБС остаётся системой учёта и подтверждения условий в MVP.                                                                 |
| F-12     | Functionality  | Клиент должен получать СМС после подтверждения размера ставки и после открытия депозита.                                     | Да  | Требует событий/статусов процесса и интеграции с SMS-шлюзом.                                                               |
| F-13     | Functionality  | Ставки по депозитам должны вестись в системе, а не только в XLS-файлах.                                                      | Да  | Ключевое требование к данным; влияет на выбор владельца данных и целевой системы хранения.                                 |
| F-14     | Functionality  | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов должны иметь возможность работать со ставками.                           | Да  | Требует ролевой модели доступа и совместного процесса согласования ставок.                                                 |
| F-15     | Functionality  | Процесс согласования ставки по заявке желательно реализовать в АБС.                                                          | Да  | Влияет на границы ответственности АБС и интеграцию с цифровыми каналами.                                                   |
| U-01     | Usability      | Интерфейс подачи заявки должен быть максимально удобным для клиента.                                                         | Нет | Требование важно для UX, но само по себе не задаёт архитектуру без конкретных метрик.                                      |
| U-02     | Usability      | Интерфейсы сайта и интернет-банка должны соответствовать принятой в банке дизайн-системе.                                    | Нет | Нужно использовать привычные цвета и брендированные элементы.                                                              |
| U-03     | Usability      | Клиент должен видеть понятные статусы заявки и результата обработки.                                                         | Да  | Добавленное требование: снижает нагрузку на кол-центр и требует модели статусов заявки.                                    |
| R-01     | Reliability    | Сервисы процесса открытия депозитов должны работать 24/7.                                                                    | Да  | Влияет на отказоустойчивость, мониторинг, регламентные работы и эксплуатационную модель.                                   |
| R-02     | Reliability    | Требуемая доступность сервисов - 99,9%.                                                                                      | Да  | Требует проектирования SLO/SLA, отказоустойчивости и контроля доступности.                                                 |
| R-03     | Reliability    | Сбой ЦОД не должен приводить к длительной недоступности интернет-банка.                                                      | Да  | Требуется сценарий работы/переключения на резервный ЦОД.                                                                   |
| R-04     | Reliability    | Новая онлайн-подача заявок не должна ставить под угрозу работоспособность АБС.                                               | Да  | База АБС уже перегружена; необходимо ограничивать нагрузку и избегать жёсткой зависимости цифровых каналов от АБС.         |
| R-05     | Reliability    | При сбоях интеграций заявка не должна теряться.                                                                              | Да  | Добавленное требование: нужны надёжная фиксация заявки, повторная обработка и идемпотентность.                             |
| R-06     | Reliability    | СМС-уведомления должны отправляться повторно или попадать в очередь повторной отправки при временной ошибке.                 | Да  | Добавленное требование: важно для подтверждения операции и информирования клиента.                                         |
| P-01     | Performance    | Отклик по операциям в клиентских каналах должен занимать миллисекунды.                                                       | Да  | Требование требует уточнения SLO, но уже влияет на кеширование, асинхронность и ограничения интеграций.                    |
| P-02     | Performance    | Загрузка справочных данных не должна занимать больше секунды, как сейчас при платежах.                                       | Да  | Необходимо устранить узкое место со справочными данными, вероятно через кеширование/локальное чтение.                      |
| P-03     | Performance    | Сервисы интернет-банка должны выдерживать требуемую нагрузку при росте числа онлайн-заявок.                                  | Да  | Сейчас интернет-банк работает в одном ЦОД на одной группе серверов; нужно масштабирование.                                 |
| P-04     | Performance    | Нужно предусмотреть равномерное горизонтальное масштабирование и распределение запросов между серверами, приложениями и ЦОД. | Да  | Влияет на балансировку, stateless-подход и хранение состояния.                                                             |
| P-05     | Performance    | АБС может масштабироваться только вертикально из-за базы данных.                                                             | Да  | Ограничение производительности: нагрузку на АБС нельзя наращивать линейно через новые онлайн-каналы.                       |
| S-01     | Supportability | При доработках нужно максимально использовать технологии, которые уже есть в банке.                                          | Да  | Предпочтительны MS SQL, Oracle и совместимые с текущими платформами разработки решения.                                    |
| S-02     | Supportability | Новые технологии должны быть совместимы с существующими платформами разработки.                                              | Да  | Ограничивает выбор технологического стека для MVP.                                                                         |
| S-03     | Supportability | Желательно использовать технологии, по которым внутри банка уже есть экспертиза.                                             | Да  | Снижает операционные риски и зависимость от внешних подрядчиков.                                                           |
| S-04     | Supportability | Доработки SMS-функционала ядра подрядчиком лучше избежать.                                                                   | Да  | Требует найти реализацию подтверждения и уведомлений силами команды банка.                                                 |
| S-05     | Supportability | Если нужны очереди сообщений, на перспективу лучше использовать Kafka.                                                       | Да  | Важно для целевой архитектуры, но текущая платформа интернет-банка несовместима с Kafka.                                   |
| S-06     | Supportability | Нужно предусмотреть документацию для дальнейшего расширения системы.                                                         | Да  | Требуется описание API, событий, статусов заявок, моделей данных и эксплуатационных сценариев.                             |
| S-07     | Supportability | Возможный переход интернет-банка к микросервисной архитектуре следует рассматривать только в рамках открытия депозитов.      | Да  | Ограничивает масштаб изменений и помогает не превращать MVP в полную перестройку интернет-банка.                           |
| +SEC-01  | Security       | Трафик сайта при передаче заявки с Ф. И. О. и телефоном должен быть защищён шифрованием.                                     | Да  | В задании явно указана чувствительная информация; минимум требуется TLS.                                                   |
| +SEC-02  | Security       | Данные интернет-банка при передаче должны быть защищены механизмом шифрования.                                               | Да  | Требование относится к клиентским данным, счетам, суммам и операциям.                                                      |
| +SEC-03  | Security       | Доступ сотрудников депозитного и кредитного бэк-офиса к ставкам и данным клиента должен разграничиваться ролями.             | Да  | Учитывает ограничения ИБ из текущего ландшафта: сотрудники депозитов и кредитов не должны видеть лишние данные друг друга. |
| +DATA-01 | Data           | Требуется единый источник актуальных депозитных ставок для сайта, интернет-банка, кол-центра и бэк-офиса.                    | Да  | Устраняет расхождение данных между XLS, АБС и цифровыми каналами.                                                          |
| +DATA-02 | Data           | Требуется хранить состояние заявки и результата обработки.                                                                   | Да  | Нужно для обработки менеджером, отправки СМС после подтверждения ставки и после открытия депозита.                         |
| +I-01    | Interface      | Сайт и интернет-банк должны передавать заявки в контур обработки депозитов, минимизируя прямую нагрузку на АБС.              | Да  | Учитывает чувствительные данные с сайта и риск перегрузки базы АБС при онлайн-подаче заявок.                               |
| +I-02    | Interface      | Интеграция с SMS-шлюзом должна поддерживать подтверждение операции и информационные уведомления.                             | Да  | Нужны два сценария: СМС-код для открытия депозита и уведомления после изменения статуса.                                   |
| +I-03    | Interface      | Система кол-центра должна получать заявки с сайта или иметь доступ к ним для обработки менеджером.                           | Да  | Требуется для сценария, в котором менеджер кол-центра звонит новому клиенту после заявки на сайте.                         |
| +R-01    | Restrictions   | MVP должен сохранить ручную обработку заявки менеджером бэк-офиса и очную идентификацию новых клиентов в отделении.          | Да  | Ограничивает автоматизацию: цифровая подача заявки не означает полностью онлайн-открытие депозита для нового клиента.      |
| +R-02    | Restrictions   | Новая функциональность должна учитывать перегруженность БД АБС и вертикальный характер масштабирования АБС.                  | Да  | АБС нельзя использовать как масштабируемый онлайн-бэкенд для резко выросшего потока заявок.                                |
| +R-03    | Restrictions   | Текущая версия интернет-банка несовместима с Kafka.                                                                          | Да  | Ограничение влияет на выбор интеграционного подхода для MVP, даже если Kafka рассматривается как перспективная технология. |
